# M3 — JavaFX CAD workbench

Date: 2026-11-04 (Europe/Warsaw). Follows M2 commit `e46c107` and M3
implementation checkpoint `a40162a`, subsequently formatted in `c60def9`.

**M3 is accepted on Windows and Ubuntu WSL.** The full root checks pass all
**36 tests** (23 engine, 3 CLI, 6 controller, 4 Robot), with no failures or
skips, on Windows, WSLg and Xvfb/Mesa. Both installed development launchers
also pass real rendered-window smoke tests: Direct3D on Windows and Mesa ES2
under WSLg. Spotless passes as part of the root checks.

The earlier Windows graphics and interaction failures are retained as diagnostic
history. After the user restored the active display, Direct3D became available.
Mouse-event tracing then isolated the missed clicks to JavaFX Robot's monitor
coordinate conversion on the mixed-DPI desktop. Centering test windows on the
primary display resolved those failures without changing application behavior,
forcing a display scale, skipping tests or weakening assertions. The agent
configuration remains unchanged.

## Automated evidence

The GUI Robot workflow constructs the reference part through controls and
two-point viewport drawing, saves/reopens, changes thickness to 8, rolls back,
undoes/redoes, exports 3MF and consumes the external fixture from a directory
containing spaces with a nondefault label option. An independent CLI process
edits the 5 mm baseline to the identical document, checks stable feature IDs,
bounds (0,0,0)–(60,40,8), volume 19099.469035085127 mm³ and the through-hole.
Picking and camera gestures use real mouse input. Both palettes are rendered.

Other Robot cases cover signed extrusion on offset Z=12, typed −3 mm extrusion,
drag cancellation with Escape, exactly one undo entry per committed drag,
invalid dimensions, broken-reference repair, file keyboard shortcuts and
Save/Discard/Cancel. Controller tests cover preview transactions, atomic
snapshots, stale/coalesced results, file failures, failed-build geometry removal
and the orientation-preserving Z-up conversion.

The initial rendered-window smoke passed on Windows at 14:40 and under WSLg
before the editing tools were added. WSLg required Mesa's ES2 pipeline with
`prism.forceGPU=true`; the launcher supplies that WSL default. Subsequent
Windows runs could not initialize Direct3D: a read-only probe reported
`D3DERR_NOTAVAILABLE` and zero adapters, even on the unlocked input desktop.
A temporary process-scoped display-awake request did not resolve it and was
released immediately. Once the user restored the active display, the installed
launcher created a D3D9Ex device on the NVIDIA RTX 3060 and printed
`GUI_SMOKE_PASS`. No driver or persistent OS graphics setting was changed.

The restored display exposed a separate test-fixture issue. The
[JavaFX 21 Windows screen conversion](https://github.com/openjdk/jfx21u/blob/21.0.13%2B1/modules/javafx.graphics/src/main/native-glass/win/GlassScreen.cpp)
chooses a monitor by distance to its center. With adjacent 150% and 100%
displays, an intended timeline-button click at approximately (89,871) reached
the rollback slider at (59,909). The
[mouse-event trace](M3/windows/mixed-dpi-robot-diagnostic.txt) records the
coordinate mismatch. Test windows now center on the primary display instead
of sitting near its left edge. The signed-extrusion, file-prompt, reference-part
and broken-reference workflows then all passed using actual JavaFX Robot input
at the existing display scale.

Workbench dialogs use window-local modal overlays after WSLg repeatedly lost
keyboard focus when a separate GTK dialog closed. The real shortcut regression
passes with the overlay; native Browse remains available. Robot fixtures keep
their windows foreground, wait for layout/dialog readiness and activate native
windows before typing. Key entry is paced to avoid dropped keyboard events. Dynamic
export options are scrollable. Windows CLI parity uses a launcher classpath
wildcard string rather than an invalid Windows filesystem path.

## Platform details and limits

- Windows 11 x86-64, Amazon Corretto 21.0.6.7.1, NVIDIA RTX 3060 Laptop GPU,
  driver 32.0.15.9186, JavaFX Direct3D; adjacent 150% and 100% displays.
- Ubuntu 24.04.3 x86-64, OpenJDK 21.0.12.1, WSL2 kernel
  6.18.54.1-microsoft-standard-WSL2, WSLg 1.0.79, Mesa 25.2.8 llvmpipe
  OpenGL, GTK 3.24.41.
- JavaFX 21.0.13, OCCT 7.9.0, Gradle 9.1.0 on both platforms.
- Xvfb 21.1.12, software Mesa, 1600×1000×24 for the CI-path interaction run.

All results above are automated local checks, not a manual usability study.
The development application uses classpath JavaFX (which prints an unnamed
module warning) and an installed Java 21 runtime. A bundled JVM/installer is
outside M3. Bambu Studio dimension/layer compatibility remains explicitly
**pending**, as allowed in M2. macOS, manufacturing placement, slicing, supports,
printer hardware and persistent generated-face references are not qualified.
