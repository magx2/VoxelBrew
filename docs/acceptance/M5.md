# M5 acceptance — packaged runtime and platforms

Implementation follows M4 commit `af09202`. Each frontend now has a jpackage app
image with Java 21, host OCCT and runtime notices. `check` includes standalone
package verification, and the CI matrix adds macOS 15 Intel with Xcode 16.4.
The macOS slicer DMG is SHA-256 pinned and extracted without installing drivers.

The focused Windows package run passed in 30s; Ubuntu passed in 30s. The first
Ubuntu attempt selected the system JRE and failed because `jmods` was absent.
Packaging now selects a Java compiler toolchain and diagnoses a missing full JDK.
The existing SDKMAN Temurin JDK supplies the Linux runtime; no system Java change
was required. Commands:

The child launchers run without Java on PATH or JAVA_HOME. CLI subprocesses
reopen the reference fixture, edit 8→5→8 mm, verify volume 19099.469… mm³ and the
empty hole center, export STL/3MF and load a consumer-built plugin with a
nondefault option from a directory containing spaces. Python independently
reads facet coordinates and the 3MF model. Existing full engine tests retain
topology, radial deviation, instance transform and real-slicer coverage.

The packaged GUI builds native geometry and uses JavaFX Robot to click its
rendered body, requiring a real triangle pick. It retains a screenshot and the
bundled runtime's version/location. The full workbench Robot suite remains part
of the root check; packaging does not replace gesture acceptance.

On 2026-11-04 both full root checks passed with no exclusions, including all 55
JUnit tests and both packaged-launcher checks. Linux ZIPs were also extracted to
`.tools/M5 extracted images.EOdUaI`; the relocated CLI repeated native inspection
and the relocated GUI rendered/picked successfully with no Java on PATH. This
also verified the ZIP's Unix executable permissions.
The Windows ZIPs were extracted to `.tools/M5 extracted images 15366b6ea3de4a8f9e35b099f14ae8c1`;
both complete packaged CLI and GUI checks passed again from that relocated path.
The CI cache retains only pinned OCCT sources/compilation; the bridge and all
checks still run, and cache hits do not count as platform qualification.

Evidence: `.tools/m5-package-focused.log`, `.tools/m5-root.log`; each frontend's
`build/package-artifacts/commands.json`, `result.json` and per-run directory.
GUI per-run directories include `packaged-gui.png` and `packaged-gui.txt`.
CI uploads those records with JUnit XML and images. Build/archive commands and
user launchers are in [packaging](../packaging.md).

No installer integration, signing/notarization, macOS arm64 or physical-printer
claim is made by these app-image checks.

The first hosted macOS attempt passed formatting, selected Xcode 16.4, and verified
both native archives and the slicer DMG. Bootstrap then failed because it assumed
a `.pkg` at the image root. The bootstrap now discovers the application bundle
first, with recursive package extraction as a fallback; it does not install
drivers or modify `/Applications`. macOS acceptance remains pending its rerun.

The corrected macOS bootstrap passed and the real OCCT/JNI build succeeded. The
next attempt failed after 31m52s because JDK 21's Mac bundler rejected app version
`0.1.0`. macOS metadata now uses bundle build number `1.0.0`; product/archive
versioning is unchanged. CI now retains a completed OCCT installation even if a
later package/test step fails, guarded by successful bridge configuration.
Full macOS runtime and GUI acceptance remains pending.
