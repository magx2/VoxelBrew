## Routine archive qualification

The follow-up to M4 status commit `1a0af12` closes the gap between the original
app-image gate and the ZIP users receive. `platformCheck` now includes
`releaseArchiveCheck`; `check` inherits it for both frontends, and macOS
`headlessPlatformCheck` includes the CLI archive only. The release workflow uses
the same gate, without repeating the archive tests in separate steps.

The check extracts each actual Gradle ZIP to a path containing spaces, verifies
Unix launcher permissions, rejects unexpected top-level entries, and runs the
packaged CLI workflow or GUI rendering/picking smoke test there. Both the original
and relocated images are checked with external Java and native-library search
overrides removed. Acceptance additionally checks:

- Installation component, product version and OS/CPU metadata.
- The bundled Java executable reports Java 21, the expected architecture and a
  `java.home` inside the tested image.
- Windows/Linux native dependencies match the build by SHA-256. macOS packaging
  inputs match the native build, and relocated libraries match the original app
  image after jpackage's signing step.
- Project and third-party notices match the source copies; Java runtime notices
  are present.
- A successful archive record includes the tested ZIP's SHA-256 and size, with
  links to runtime, command and package evidence. An earlier successful record
  is removed before a new attempt so a failure cannot leave a stale pass.

Commands are the unchanged full root gates below. Focused reproduction is
`./gradlew :cli:releaseArchiveCheck :gui:releaseArchiveCheck` (use `gradlew.bat`
on Windows and Xvfb/Mesa on Ubuntu). Evidence is under each frontend's
`build/package-artifacts/archive/`, including `archive-result.json`, `result.json`,
`commands.json`, runtime output and GUI screenshot. Local full-check logs for
this follow-up are `.tools/m5-completion-root.log` in each checkout. Hosted
evidence retains the requested three-day lifetime.

The next hosted run passed the packaged macOS CLI, including native editing,

force-GPU setting cannot supply that context. JavaFX's 2D software pipeline does
not satisfy the 3D gate, and no GUI tests were skipped to hide the failure.
